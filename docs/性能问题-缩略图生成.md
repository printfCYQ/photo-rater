# 性能问题：批量缩略图生成耗时过长

## 现状

| 指标 | 数值 | 目标 |
|------|------|------|
| 256 张图耗时 | ~28s | <5s |
| 单张解码 avg | ~858ms | <50ms |
| 单张解码 min | ~397ms | — |
| 单张解码 max | ~1843ms | — |

## 根因分析

瓶颈在 Rust 端 `batch_get_thumbnails`，每张图需要：**JPEG 解码 → resize → JPEG 重新编码**。

当前优化程度：
- `zune-jpeg` / `zune-core` / `jpeg-decoder`：opt-level=2 ✅
- `image` crate（resize/encode 逻辑）：opt-level=1 ⚠️
- resize filter：`Nearest`（已在 400px 缩略图使用）
- 并行：rayon 并行处理

性能演进：
1. 无优化（opt-level=0）：~52s（avg 1.6s/张）
2. 全局 opt-level=2：OOM 无法编译
3. per-package opt-level=2（zune 系列）+ Triangle：~68s ❌
4. Nearest filter：~28s（avg 858ms/张）

## 己尝试的方案

- ~~全局 opt-level=2~~ → OOM 被 kill
- ~~per-package opt-level=2 全 image 相关~~ → OOM
- ~~Triangle → Nearest~~ → 28s，仍太慢
- ~~zune-jpeg 降采样解码~~ → API 不支持

## 待尝试的方案

### 方案 A：release 模式编译（推荐优先尝试）
`cargo build --release` 可以用全局 `opt-level=3` + LTO，不会 OOM（release 不需要 debuginfo，内存占用小很多）。预计单张 <50ms。
- 缺点：编译慢，开发调试不方便

### 方案 B：渐进式加载（需求侧优化）
不等全部 256 张生成完才显示，改为**流式返回**：deocde 完一张就通过 Tauri event 推给前端，前端逐步替换占位图。
- 优点：用户感知延迟大幅降低
- 缺点：需要改前后端通信模式

### 方案 C：缓存预热
导入相册时异步后台生成所有缩略图，用户打开相册时 100% 缓存命中。
- 优点：打开相册瞬间显示
- 缺点：导入时需要等待 / 后台任务

### 方案 D：混合模式
- `pnpm tauri dev` 日常开发 → 接受慢（调试用）
- `pnpm tauri build` 发布/实际使用 → release 模式，快到飞起
- 告诉用户：**开发模式慢是正常的，打包后就好了**

## 临时建议

当前 28s / 256 张（avg 858ms/张）虽然不快，但：
- 同一个相册第二次打开时缓存 100% 命中 → 瞬间加载
- 首次导入 + 打开才会经历全量生成
- 日常使用影响有限
